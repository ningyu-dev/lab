# 001 · 为什么规范知识库不能做 RAG

编号 001 ｜ 2026-10-09

## 结论

规范知识库做**结构化**，不做 RAG。RAG 在本项目中降级为「规范原文查阅辅助」，不参与任何计算和判断。

## 讨论的起点

想给一个给排水设计 agent 做规范知识库时，最自然的想法是 RAG：把规范 PDF 切块向量化，用户问什么就检索什么。这个方案看起来能省掉大量人工录入的工作。

结论是不能用。理由分两层。

## 第一层：RAG 的返回形态和校验需求不匹配

校验一条规则，系统需要的是**可比较的值**。

```
用户问："天沟坡度够吗？"
需要：  value = 0.005, comparator = ">=", actual = 0.003  →  判定不通过
RAG 给：  "金属天沟的纵向坡度不应小于百分之零点五……"（一段文字）
```

文字形式对人是足够的，对程序是不够的。要让程序用，必须再解析一次——而解析的失败率就是错误率来源。**多引入一层不确定性，正是要避免的。**

## 第二层（更关键）：RAG 输出不可复现

这是决定性理由。

同一份规范、同一句提问，两次检索可能返回不同段落。如果系统的判断依赖 RAG 的输出，那么：

- 同样的输入，结论可能不同
- 出错时无法定位是哪一步错了
- 设计文件里写的依据，无法回溯到具体是哪一次检索

**RAG 的行为本质上是概率性的，而工程交付物要求确定性。**这两者不兼容。

## 可复现性怎么保证

关键不是「模型更好」，而是**把所有决策依据固化到数据里，让模型没有自由发挥的空间**。

结构化后的规则长这样：

```json
{
  "rule_id": "GB50015-2019-5.2.11",
  "standard_year": 2019,
  "subject": "gutter_longitudinal_slope",
  "comparator": ">=",
  "value": 0.005,
  "mandatory_level": "strong_clause",
  "provenance": { "page": 87, "extracted_by": "manual" }
}
```

这条数据的每一个字段都是确定的：值是多少、哪个版本、哪一页。给定它，任何人、任何机器、任何时候都会得出同样的判断。

## 这个决策的普适性

这不是给排水特有���。任何**结果需要追责**的场景都适用：

- 合规检查 —— 依据哪条法规必须能说出来
- 医疗辅助 —— 剂量计算必须可复核
- 金融风控 —— 拒绝理由必须可申诉

共同点是：**错误有代价，且代价不由系统承担。** 这类场景里，模型的任务不是「回答」，而是「在受限空间内做选择，并且每个选择都能说清楚依据」。

## 代价

人工录入很慢，是整个项目最耗人的部分。300–400 条规范条文，两人配合，预计 2–4 周。

这个代价无法绕��，只能接受。**它的存在本身就是护城河 —— 别人也得走一遍。**

## 什么时候该重新审视这个决策

如果出现以下情况，说明前提变了：

- 规范原文变成了机器可直接查询的结构化接口（不用自己录入）
- 项目从「辅助」变成了「研究工具」，可复现性不再是硬要求
- 出现了一批条文，只有自然语言描述而无可量化阈值 —— 这部分可能只能用 RAG，且必须标注为「仅供参考，不可作为校核依据」

最后一条其实已经在 schema 里预留了位置：`rule_type` 允许 `categorical` 和 `constructive` 类型，它们的值就不是单一数字，语义上比阈值模糊。**处理这类条文时，判断标准应该比阈值更保守。**
